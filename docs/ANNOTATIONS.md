# ✍️ Opt-in Google Analytics annotations

The official Google Analytics MCP server includes `create_property_annotation`, which is absent from SednaLabs' read-only Rust reference. Synmetra includes the tool but keeps it **disabled and hidden by default**.

To expose the write tool locally, explicitly start `synmetra serve --allow-write`. The selected Google OAuth identity must independently have the `https://www.googleapis.com/auth/analytics.edit` scope and appropriate property role; the normal native `synmetra auth login` requests **read-only** access. Only `synmetra auth login --client-id-file PATH --allow-edit` explicitly requests both `analytics.readonly` and `analytics.edit`. The server separately requires `--allow-write` to advertise the mutation tool. Mutation preflight accepts only the private native OAuth store when its **recorded granted scopes contain the exact `analytics.edit` URL**. A `SYNMETRA_GOOGLE_ACCESS_TOKEN` override cannot prove its scopes locally and is therefore **rejected for writes**, even if it might be valid at Google. Missing credentials and insufficient scopes produce distinct redacted errors before network access. The Google property-role permission is checked by Google and may still yield HTTP 403; a local scope check never establishes property eligibility.

Annotation inputs: `property_id`, `title` (1–60 characters), `start_date` (YYYY-MM-DD), optional `end_date` (not earlier than start), optional `description` (up to 150 characters), `color` (PURPLE, BROWN, BLUE, GREEN, RED or CYAN; default BLUE). ORANGE is Google-reserved and rejected. Google calls use `v1alpha` Admin API over rustls, and writes never auto-retry.

**Verification:** synthetic tests validate color/date/length restrictions, API path, flag-dependent tool visibility, and rejection without credentials. No live annotation has been created; live write acceptance is a separate user-authorized test-property gate. MCP client host confirmation is recommended; Synmetra's explicit `--allow-write` is an operator capability gate, not a per-call interactive confirmation.

**Write audit boundary:** Every direct `create_property_annotation` attempt now emits one machine-readable JSON line on **stderr** with a UTC RFC 3339 timestamp, fixed action name and fixed outcome (`blocked_read_only_profile`, `blocked_edit_scope`, `invalid_input`, `provider_accepted`, or `provider_failed`). The record is deliberately limited to `timestamp`, `action`, `outcome` and `details_redacted`. It excludes property identifiers, annotation titles, dates, descriptions, access tokens, OAuth state, provider messages and provider bodies. The native MCP transport's stdout stays reserved for protocol messages. The read-only handler rejects direct calls even if another layer erroneously exposes its route. CI tests cover the audit whitelist and direct-call guard; no external log collector or retention policy is yet claimed.

**Host approval boundary:** If the MCP client offers per-call write approvals, configure it to require explicit approval for `create_property_annotation`. Synmetra cannot force or attest to a third-party client's approval dialog; `--allow-write` is an operator capability flag, **not** a substitute for per-call confirmation. Full confirmation behavior remains unaccepted until supported host verification.

Do not expose `--allow-write` over a publicly reachable HTTP transport.

**Native edit consent:** The new `auth login --client-id-file PATH --allow-edit` mode explicitly requests Google Analytics read and edit scopes with PKCE. Regular login remains read-only, and the token response must include *every* requested scope before credentials are saved. Locally stored read+edit credentials do not enable writes by themselves; the MCP server still defaults to no `create_property_annotation` tool. Synthetic scope tests pass only after CI, and an actual Google consent / annotation write remains unverified.

### Scope-denial versus Google 403

| Failure | MCP error code / category | What is actually established | Safe action |
| --- | --- | --- | --- |
| No native OAuth credential | `AUTH_NOT_CONFIGURED` / authentication | No locally usable Google credential has been configured | Use `auth doctor` and consent through the account owner's browser only if authorized |
| Native OAuth grant lacks exact `analytics.edit`, or token override has no locally attestable scope | `EDIT_SCOPE_REQUIRED` / authorization | The mutation is **blocked before any Google request**; no broader OAuth consent or token refresh is initiated by the mutation | Explicitly reauthorize using `auth login --allow-edit` with permission, then restart with `--allow-write` |
| Google responds HTTP 403 after a locally verified edit-scope preflight | `GOOGLE_HTTP_ERROR` / upstream, `status_code=403` | The **provider** denied the request; this alone does not prove which of Google Analytics property role, API activation, quota-project permission or other policies caused it | Check the requested account/property role and API configuration independently, without blindly expanding scopes |

The server never silently escalates OAuth permissions after a 403 or replays an annotation write. These distinctions are covered by offline synthetic tests, **not** by a real GA4 account role trial. The stored scope is merely the OAuth grant; Google remains the authority on live property permission, and client-side per-call confirmation stays a separate release gate.
