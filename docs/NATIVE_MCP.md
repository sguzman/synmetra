# 🦀 Native MCP implementation status

The executable `synmetra` now boots an experimental **read-only** MCP stdio server using the official Rust `rmcp` SDK. Twenty read-only tool names are advertised by default because they have provisional handlers: `get_account_summaries`, `get_property_details`, `list_google_ads_links`, `list_property_annotations`, `get_custom_dimensions_and_metrics`, `run_report`, `run_realtime_report`, `get_account_data_sharing_settings`, `get_property_data_retention_settings`, `run_pivot_report`, `batch_run_reports`, `check_report_compatibility`, `run_property_access_report`, `run_account_access_report`, `preview_report_request`, `run_funnel_report`, and `run_conversions_report`.

An additional `create_property_annotation` tool is enabled only by `--allow-write`; see [annotation policy](ANNOTATIONS.md). **Not feature parity.** These handlers are an initial slice: they still need upstream parameter-level and output contract comparisons, authorized live GA testing, complete filtering and pagination cases, secure remote HTTP transport, and DuckDB scratchpad. The 36-name ledger remains a *target* inventory, not an advertised set of working tools.

Build and run: `cargo run --bin synmetra -- serve`. For a short-lived local development token, set `SYNMETRA_GOOGLE_ACCESS_TOKEN` to a Google OAuth access token granted `analytics.readonly` (the process must be restarted on expiry). Tokens are neither printed nor persisted. Do not put the token in command-line arguments, shell history, source, CI secrets, or public issue logs. Without a token, the server starts but tools return a structured missing-credentials error.

MCP uses stdout exclusively. No credentials, real GA property IDs or private report bodies are used in automated CI; tests use synthetic fixtures. Network calls target fixed Google API hosts with rustls, bounded timeouts, 4 MiB response guard and no redirects. No Python or npm required by the binary. Native OAuth is coded and offline-tested; authorized real-Google login and refresh QA remain outstanding.

Additional read-only endpoints now include account data sharing, property retention, pivot and batched reports, metric compatibility, and account/property access reports. Advanced report tools currently take a provider-style `request` JSON object, not complete SednaLabs parameter schemas, so upstream parity remains open. Google access reports require Administrator permissions. Batch reports reject zero or more than five requests. The HTTP client refuses unknown operation names.

## 🔑 Native OAuth setup

Use a Google Cloud **Desktop** OAuth client JSON file (from an enabled Analytics Admin + Data API project), then run `synmetra auth login --client-id-file /path/to/client.json`. Synmetra binds a random port on `127.0.0.1`, opens the browser with `xdg-open`, and uses PKCE S256 plus a random callback state. Optional native CLI flags are `--account EMAIL` (Google `login_hint`), `--callback-port PORT` (an explicit loopback port instead of the default ephemeral port), and `--headless` (print the URL without launching a browser). `--allow-edit` requests the separate read+edit scope and still requires server `--allow-write` to expose mutation tools. The MCP `ga4_auth_login_command` helper can render these flags with shell-quoted paths and account hints; it does not initiate OAuth. The pinned upstream `quota_project` and `shared_adc=true` options are explicitly rejected by Synmetra rather than silently issuing unsupported commands: native token storage remains private and quota-project routing requires a separate verified implementation. Access is requested with **analytics.readonly** only and `access_type=offline`; no Python, npm, or gcloud is invoked. `synmetra auth status` reports whether private credentials exist; `synmetra auth logout` clears local credentials.

Credentials are written as `$XDG_CONFIG_HOME/synmetra/credentials.json` (or `~/.config/synmetra/credentials.json`) with directory mode 0700 and file mode 0600. Tokens never enter public logs or CLI arguments. The process automatically refreshes an expiring access token using its private refresh token; `SYNMETRA_GOOGLE_ACCESS_TOKEN`, if explicitly set, overrides local storage and does not auto-refresh.

**Security/acceptance:** OAuth is implemented with synthetic callback and PKCE tests, but no real Google login or refresh flow has yet been verified. An interactive OAuth login necessarily requires a one-time browser authorization by the account owner. Do not commit OAuth client JSON, credentials.json or browser callback URLs.

The new v1alpha conversion and funnel handlers are intentionally **eligibility-sensitive**: conversion reports use v1alpha `runReport` with conversionSpec or conversion metrics; funnel reports use v1alpha `runFunnelReport` and bounded step counts. Preview constructs a report body without network access. These are initial request routes rather than completed upstream contract parity.

Three new read-only setup helpers provide commands and safe credential status without returning tokens, client identifiers, or private paths.

The optional loopback Streamable HTTP transport has an authenticated MCP initialization integration test (GitHub Actions run 40204566566). It does not support public remote multiuser access or TLS. See [HTTP policy](HTTP.md).

The provisional `run_conversions_report` handler now takes the official required fields directly (property ID, date ranges, dimension/metric names and conversion specification). It validates supported v1alpha conversion dimensions/metrics, action identifiers, attributions and the 50-action limit before forming a Google request. SednaLabs' pagination/output projection controls, full response schema and live eligibility still require separate parity acceptance.

The provisional `run_funnel_report` tool now uses the official required `funnel_steps` argument and normalizes simple event steps, named steps, breakdowns, next actions, dates and up to four nonempty segments into Data API v1alpha JSON. Invalid/ambiguous step expressions and oversized payloads fail locally. More specialized SednaLabs funnel controls, output projections and live property eligibility remain unverified.

Three additional read-only tools now use typed upstream argument shapes rather than generic provider request blobs: `run_pivot_report` (explicit dates, dimensions, metrics and pivot structures), `batch_run_reports` (1–5 report entries) and `check_report_compatibility` (dimension and metric lists). Input validation is synthetic-testable without Google credentials. Full SednaLabs optional controls, output projections and live API eligibility are separate unverified gates.

Both Admin access-report tools now take explicit required date-range, dimension and metric arguments instead of generic provider JSON. The request builder uses Admin-specific `dimensionName` and `metricName` fields, with bounded input validation and synthetic tests. Authorized Administrator-role GA4 integration, optional SednaLabs projection controls and filter normalization remain unverified.

## 🔎 Bounded GA4 collection pagination

Account summaries and Google Ads links follow Google Admin API `nextPageToken` and merge multiple pages in source order, with a 100-page request limit. To bound persistent-agent memory, Synmetra enforces a maximum of 10,000 collected entries and 16 MiB of serialized items; it rejects overlong (over 1024-byte) or repeated continuation tokens. Two-page, empty/replayed-token, and oversized-result cases are tested against local HTTP mocks. These ceilings can reject very large legitimate properties rather than silently returning incomplete totals. They are implementation safeguards, not full real-Google acceptance.

## 🧪 Structured and shorthand filters

`dimension_filter` and `metric_filter` accept bounded Google FilterExpression objects, JSON-encoded objects, or equality shorthand. Examples: `country==Mexico`, `sessionDefaultChannelGroup=="Paid Other"`, `sessions==7`, and `engagementRate==0.5`. Dimension shorthand builds an exact string filter; metric shorthand builds an integer or finite decimal numeric filter. Ambiguous values, malformed nested expressions, and excessive depth/size are rejected before Google requests. Other shorthand operators and live field eligibility are not implemented.

### 📑 Bounded Admin pagination options

`get_account_summaries`, `list_google_ads_links`, and `list_property_annotations` now expose the pinned upstream optional `page_size` and `max_pages` controls. The implementation bounds page size to 1–200, page count to 1–100, total items to 10,000 and aggregate response to 16 MiB, and rejects reused/oversized pagination tokens. Explicitly stopping at a user-specified page count returns `truncated: true` and a `nextPageToken` rather than claiming the collection is complete. Synthetic HTTP tests validate the transmitted `pageSize` and bounded partial-result contract; authorized live account testing is still required.

See the [Contract V1 compatibility policy](CONTRACT.md) for the current dual structured/text envelope, stable error codes, and outstanding response-parity gates.

Explicit edit-scoped OAuth for optional annotation creation: `synmetra auth login --client-id-file /path/to/desktop-oauth.json --allow-edit`. This requests both `analytics.readonly` and `analytics.edit`, verifies that both scopes were granted, and stores the permission tier privately. Default login remains read-only, and all write tools remain hidden without a separately explicit `synmetra serve --allow-write`. No real Google consent has been verified yet.

## 📊 Explicit tabular response projection

`run_report`, `run_realtime_report`, `run_conversions_report`, and `run_pivot_report` preserve raw Google response shapes by default. They now accept optional `output_mode` (`rows`, `tuples`, `scalar`, or `compact`), `summary_only`, `max_rows` (1–1000), and `max_cell_chars` (1–2048). Supplying one of these opts into a bounded Contract V1-shaped response. Projected metadata includes the actual number of returned rows, the provider's row count when known, `row_count_total_known`, truncation, columns, and available quota/warning metadata. Dimension label strings are clipped by Unicode scalar values instead of cutting UTF-8 bytes. Numeric metric strings are **never clipped**, because shortening decimal or integer text would silently change its value; original Google metric-header types (such as `TYPE_CURRENCY`) appear as `meta.columns[].ga4_type`, and supplied `metadata` (including currency/time-zone context) stays under `meta.ga4`.

The projected response is **not complete SednaLabs compatibility**. `run_report` now supports query-bound historical pagination via `meta.next_cursor`: reuse the token in the next `run_report` call with the same property, dates, metrics, dimensions and filters, but omit `offset`. Tokens use the bounded `v1:<sha256-query-hash>:<offset>` shape and reject changed queries, malformed tokens and mixed cursor/offset. Pagination is not a Google snapshot and may change when property data updates. `run_conversions_report` supports the same opt-in bounded historical cursor projection; `run_pivot_report` projects rows and retains Google `pivotHeaders` inside `meta.ga4` but rejects generic cursors because pivot paging uses per-axis offsets. Historical raw Google responses still accept explicit `offset`/`limit`; realtime cursors and nonzero realtime offsets remain rejected. Other-tool tabular projections and authorized live Google acceptance remain open.

## ✅ Compatibility-only preflight

`check_report_compatibility` now calls Google's dedicated `properties/<id>:checkCompatibility` endpoint instead of simulating a report request. Empty `dimensions` and `metrics` arrays request a compatibility inventory, while dimension-only and metric-only probes are also supported. The special property identifier `0` (or `properties/0`) is accepted **only for checkCompatibility**, for generic standard-field discovery; it remains invalid for ordinary reporting. The response preserves the provider's `dimensionCompatibilities` and `metricCompatibilities` reason/status data. This call consumes an authenticated Google Data API request, but does not call `runReport` and does not claim to validate a live property until authorized credentials are tested.

The historical and realtime MCP handlers now accept numeric or resource-name property IDs, and report `limit` fields follow the upstream unsigned 64-bit schema while enforcing Google's documented positive 250,000-row maximum before network requests.

## 🔐 GA Admin data-access projections

Both `run_property_access_report` and `run_account_access_report` retain Google provider JSON by default. Optional `output_mode`, `summary_only`, `max_rows`, `max_cell_chars`, and `cursor` enable bounded Contract V1-style projections. Access-response `dimensionName`/`metricName` headers are normalized to named columns. Query-bound continuation tokens are scoped to the canonical `properties/<id>` or `accounts/<id>` resource and cannot be reused between them. These are read-only Admin API reports but require Google Administrator-level access; synthetic 403 tests do not prove live authorization.

## 🗂️ Pivot ordering and bounded projection limits

Google v1beta pivots require explicit positive per-axis `limit` values; Synmetra now rejects a combined product above 250,000 before an API request. Each pivot's `fieldNames` must select requested dimensions (or `dateRange`), with its own `orderBys` restricted to matching pivot dimensions or requested metrics. Per-axis `offset` and `limit` are normalized to decimal int64 strings. Pivot headers and grouped report rows remain intact in `meta.ga4.pivotHeaders`, without advertising an invented flat cursor. Reference: https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/Pivot.

The seven compatible Google Data/Admin report MCP tools advertise `rows`, `tuples`, `scalar`, and `compact` modes. Bounded opt-in projections cap returned rows and Unicode dimension labels, keep numeric metrics exact, preserve aggregate/quota metadata and disclose truncation/clipping rather than silently hiding it. Native request JSON is capped at 64 KiB and upstream Google response bodies at 4 MiB. These controls do not claim complete SednaLabs Contract V1 parity across every tool.

## ♻️ Read-only retry and quota policy

Google Analytics read-only requests (Admin GETs, historical/realtime/pivot/batch reports, v1alpha funnel and conversion reports, access reports, and compatibility probes) use a bounded retry policy for HTTP `429`, `500`, `502`, `503`, and `504`: **at most three total attempts**, with exponential base delays of 200 ms then 400 ms plus at most 100 ms of jitter. A numeric `Retry-After` header sets the minimum retry delay; values requiring more than 5 seconds (or unsupported/non-numeric HTTP-date forms) cause a terminal redacted HTTP error instead of an early retry. No retry occurs for HTTP `403`, ordinary `4xx`, non-clonable request bodies, or transport failures. Response bodies, URLs, and authorization headers are never echoed to the caller.

**Annotation creation is never retried automatically**, even after `429`, `500`, `503`, connection failures, or a `Retry-After` response. An ambiguous failed write may already have been applied upstream; callers must inspect existing annotations before intentionally submitting another create. A retrying client should never turn a read-only retry into a mutation replay. See the isolated mock tests `readonly_report_retry_is_bounded_and_never_replays_writes`, `readonly_retry_policy_honors_backoff_limits_and_never_retries_forbidden`, and `annotation_writes_do_not_retry_429_500_or_503_responses` in `src/google.rs`. Live quota limits and Google-specific HTTP-date header handling remain separate acceptance work.

## 🛡️ Pinned upstream origins and redirect isolation

Ordinary production Synmetra requests use the two hardcoded HTTPS Google API origins, `analyticsadmin.googleapis.com` and `analyticsdata.googleapis.com`. Account/property identifiers are validated as canonical positive numeric resource paths, never arbitrary URLs. The native HTTP client sets a **no-redirect** policy so an upstream 302 cannot forward OAuth bearer credentials to a different host. The only endpoint substitution is the internal `with_endpoints` fixture constructor for isolated loopback tests. This boundary is tested by `production_google_hosts_are_pinned_and_http_redirects_never_followed`, including malicious URL-like identifiers and a redirected mock report (GitHub Actions 40240180552). This test establishes the software default and redirection policy, not ownership of any live Google credentials or account authorization.

## 🧬 Scoped compatibility metadata cache

The dedicated `check_report_compatibility` call caches only successful, structurally plausible metadata for **30 seconds**, bounded to 64 entries and 128 KiB per entry. Keys are SHA-256 digests scoped to the normalized property, Google Data API endpoint, request payload and the exact bearer used for that request; credentials are never written into cache values or user-visible error messages. A changed property, bearer or request cannot reuse another result. HTTP denials, rate-limit failures and responses carrying quota snapshots are not cached. Expiration triggers an ordinary authorized refresh; repeated requests within the TTL reuse the cached metadata, but do not replace the live authenticated checks required for final acceptance.

The offline `preview_report_request` tool now provides normalized provider JSON, deterministic query hashes, pagination windows, predicted tabular and scratchpad ingest columns, and explicit `compatibility_checked=false`. It never contacts Google; use the dedicated compatibility check to resolve unknown metrics or invalid combinations before large reports. The [pinned upstream parameter audit](UPSTREAM_PARAMETER_AUDIT.md) separately documents feature-union conflicts.

## 🧭 Historical report compatibility preflight

Before an expensive historical `run_report`, call `check_report_compatibility` with the intended `property_id`, `dimensions` and `metrics`. The response still includes the **exact Google** `dimensionCompatibilities` and `metricCompatibilities` arrays in `data`, plus an additive `meta.compatibility` verdict: `compatible`, `incompatible`, `incomplete`, or `inventory`. Treat `safe_to_run: true` as meaningful only when all requested field names were explicitly returned as `COMPATIBLE`; an unspecified/missing field and an empty inventory request fail closed. Inspect `incompatible_fields` and `unchecked_fields` to revise the query. Duplicate inputs and malformed provider statuses are rejected. This preflight makes **no** `runReport` request, but it is an explicit workflow: it does **not** automatically prevent a later direct `run_report` call. Google's [checkCompatibility contract](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/checkCompatibility) covers historical/Core reports, **not realtime**; responses may change if the property metadata or permissions change. Live-account validation and full cross-tool parity remain separate gates.
